# PM-018 — Automatic Restart Paths and Duplicate Liquidation (Paper Account)

*(PM-017 was reserved for the initial watchdog incident; same causal chain, merged here.)*

**Incident window:** 2026-07-07 → 2026-07-10
**Environment:** IBKR paper account (simulated capital)
**Financial impact:** ≈ 0 (paper)
**Epistemic impact:** three days of non-deterministic broker state

> **Revision note.** An earlier public version described this paper environment as "production" and stated that the operator-halt flag was checked every cycle. The halt flag was set during this incident, but according to the August 2026 post-mortem the trading loop itself never read it until a fix that month. Those statements are corrected below.

---

## Summary

An operator halt (`systemctl stop` + `disable`) failed to keep the trading service down. Investigation found **four independent, uncoordinated mechanisms**, each capable of restarting it. Separately, a liquidation script launched twice re-submitted orders against positions that were already flat, inverting the book into unintended shorts.

The concurrent-instance fault class had been specified on July 9 as FAULT-03 in the [fault-injection harness](https://github.com/ddehanne/fault-injection-harness). The paper environment then reproduced it through several entry paths.

## Restart mechanisms identified

| # | Mechanism | Why `disable` didn't stop it |
|---|-----------|------------------------------|
| M1 | Cron watchdog (every 5 min) | Issues an explicit `systemctl start`; `disable` only blocks boot-time activation |
| M2 | Service restart policies (unit + drop-in) | Auto-restart after any non-zero exit |
| M3 | Supervisor unit (`Wants=` + internal start loop) | Pulls the target unit up every ~30 s |
| M4 | Control API with start/restart endpoint | Out-of-band explicit starts |

Four more mechanisms were found later (a second service unit, bot commands, an alerter auto-restart, a scheduled daily restart), bringing the total to eight. The cleanup took more than one pass.

## Duplicate liquidation race

Two instances of the same liquidation script ran concurrently, launched two minutes apart. Orders placed the previous day had already filled at the open. Both instances re-submitted the same orders against positions that were now flat, inverting long exposure into shorts.

A lock guard from the earlier incident ([PM-015](PM-015-INCIDENT.md)) existed, but it protected a *launcher script*, not the shared resource. The new entry path bypassed it entirely.

## Root cause

Protection was attached to **entry points** (launchers, service definitions) instead of the **shared resource**. Entry points multiply; the resource does not.

## Remediation

1. The four mechanisms were eliminated, and critical units were masked, so any restart required a deliberate, auditable `unmask`.
2. The operator-halt flag was set. *(At the time, the trading loop itself did not read this flag; see the README.)*
3. Single-writer enforcement moved to the resource level: a kernel `flock` on a dedicated lock file (INFRA-002, July 10).
4. Scripts with broker side effects must re-read broker state at action time, not at launch time; a reconciliation gate at boot followed (INFRA-003, July 14).
5. Manual interactive liquidation: all 15 orders filled; the broker was verified flat (zero positions, zero open orders).

## Lessons

- `disable` ≠ prohibition; `mask` = prohibition. A kill switch is only real if the complete start-path graph is controlled.
- Single-writer guarantees belong on the resource, never the launcher.
- Idempotence requires reading the world at action time, not at plan time.
- A fault class that is specified but not enforced will occur in operation: test harnesses predict, architecture prevents.
